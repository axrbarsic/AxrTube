# Разработка и синхронизация AxrTube

## Постоянное правило

Каждый связный проверенный этап публикуется в `axrbarsic/AxrTube`, основная продуктовая ветка `alex-personal`. Синхронизация GitHub входит в завершение изменения, а не остаётся отдельным забываемым действием. Сырой код и незавершённые эксперименты не выдаются за проверенный релиз.

## Порядок

1. Зафиксировать исходный `git status`, сохранить существующие изменения и определить границы задачи.
2. Исправить первопричину, добавить минимальные тесты реальной границы команд и состояния. Не строить отдельную копию алгоритма только для теста.
3. Выполнить адресные тесты и одну необходимую сборку. Переиспользовать действующие результаты, если код не менялся.
4. При изменении приложения установить подписанную сборку поверх существующей без удаления данных. Предпочитать Wi-Fi, фактический транспорт и блокеры указывать честно. Успешный launch не заменяет физическую проверку звука и сети.
5. Обновить README, CHANGELOG и затронутые документы по фактическому результату. Незакрытые ограничения и ожидающую физическую приёмку писать явно.
6. Проверить diff, лицензионные заголовки и отсутствие секретов. Добавлять в commit только файлы задачи. Не включать пользовательские данные, ключи, профили подписи, build/DerivedData, локальные логи и посторонние изменения.
7. Создать осмысленный commit, выполнить обычный fast-forward push в `origin/alex-personal`. Не использовать force-push для перезаписи совместной истории.
8. Перечитать опубликованные README, описание, topics и последний commit из `axrbarsic/AxrTube`. Проверить результат CI. Не считать постановку задания в очередь зелёной проверкой.

Для GitHub CLI всегда указывать `--repo axrbarsic/AxrTube`: upstream используется только для чтения и сравнения, не для публикации изменений AxrTube.

## История и откат

- Каждый commit описывает законченный связный этап. CHANGELOG связывает продуктовые изменения с датой и результатами проверки.
- Ошибочное опубликованное изменение отменяется отдельным `git revert` после определения точного commit и влияния на последующие изменения. Общая история сохраняется.
- Откат кода не откатывает автоматически пользовательские файлы и формат данных. Перед откатом проверяется совместимость медиатеки, стенограмм и настроек. Удаление приложения не является штатным способом отката.
- Теги релизов создаются для принятых сборок. До физического вердикта обновление остаётся кандидатом, даже при зелёном CI.

## Минимальная запись о завершении

Дата, причина, изменённые границы, выполненные тесты, сборка, установка и launch, физический вердикт или точный блокер, оставшиеся ограничения, commit и ссылка на GitHub. Диагностические данные устройства и подпись в публичную запись не переносятся.
